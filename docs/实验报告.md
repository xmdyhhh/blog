## 一、实验需求分析

本实验要求以成熟开源项目为基线，完成一个**可注册、可写作、可评论、可搜索**的个人博客系统，重点训练开源软件的获取、使用、分析与规范开发能力。

## 二、系统架构设计

### 2.1 技术选型

| 组件 | 选型 | 版本 | 选型理由 |
|------|------|------|----------|
| 博客核心 | Ghost | v6.59.0 | 成熟开源项目，MIT许可证，具备编辑器/标签/会员/评论/主题机制 |
| 运行环境 | Node.js | v22.23.1 LTS | Ghost 6.x 兼容矩阵要求 ^22.23.1 |
| 数据库 | SQLite | 3.x (内置) | 本地开发零配置，单文件便于备份迁移 |
| 模板引擎 | Handlebars | 4.x | Ghost 主题标准模板引擎 |
| 版本控制 | Git | 2.45.1 | 课程要求，支持分支/PR/Review |

### 2.2 为什么选择 Ghost 路线而非 RealWorld

1. **Ghost 是可直接运行的成品系统**，具备完整的认证、编辑器、会员、评论和主题机制，可将实验时间集中在二次开发而非从零搭建
2. **RealWorld 是规范仓库**，需要自行选择具体实现并固定 Commit，学习曲线较陡
3. **Ghost 主题机制成熟**，支持在不修改核心代码的前提下完成视觉和功能扩展，符合"修改边界"教学目标
4. **MIT 许可证**，允许自由修改、分发和商用，与实验兼容

### 2.4 修改边界设计

**严格遵守"不修改核心"原则**，所有二次开发在主题层完成：

| 目录 | 修改权限 | 说明 |
|------|----------|------|
| `theme/oss-blog-theme/` | ✅ 可修改 | 自定义主题源码，主要开发区域 |
| `docs/` | ✅ 可修改 | 项目文档 |
| `tests/` | ✅ 可修改 | 测试用例 |
| `scripts/` | ✅ 可修改 | 辅助脚本 |
| `runtime/current/` | ❌ 禁止修改 | Ghost 核心代码，升级时会被覆盖 |
| `runtime/versions/` | ❌ 禁止修改 | Ghost 版本文件 |
| `runtime/content/data/` | ❌ 禁止提交 | 数据库文件，含敏感信息 |

**边界设计的好处**：
1. 上游 Ghost 可随时升级，不影响自定义主题
2. 个人贡献清晰可辨，便于 Code Review
3. 符合开源软件"扩展而非分叉"的最佳实践

## 三、实现细节

### 3.1 环境搭建与问题解决

#### 问题1：Node.js 版本不兼容

**现象**：系统默认安装 Node.js v24.19.0，执行 `ghost install local` 时报错：
```
Ghost v6.59.0 requires Node.js ^22.23.1
```

**解决方案**：
1. 从 npmmirror 下载 Node.js v22.23.1 Windows 便携版（zip格式）
2. 解压到项目 `tools/node22/` 目录
3. 创建包装脚本，在运行 Ghost 前将 Node 22 路径前置到 PATH
4. 所有 Ghost 命令均通过包装脚本执行

**经验教训**：开源项目的版本兼容矩阵是硬约束，不能用"最新版"想当然，必须以项目声明的兼容矩阵为准。

#### 问题2：原生模块编译失败

**现象**：better-sqlite3、re2 等原生模块在安装时尝试本地编译，但系统未安装 Visual Studio C++ 构建工具。

**解决方案**：
1. 设置 `npm_config_better_sqlite3_binary_host_mirror` 环境变量，使用 npmmirror 预编译二进制镜像
2. 设置 `NODE_TLS_REJECT_UNAUTHORIZED=0` 解决预编译下载的证书问题
3. 成功下载预编译二进制，无需本地编译

### 3.3 自主扩展功能实现

#### 3.3.1 相关文章推荐

**实现位置**：`post.hbs` 第70-100行

**设计思路**：
1. 使用 Ghost `{{#get}}` 助手查询与当前文章 `primary_tag` 相同的文章
2. 排除当前文章本身（`id:-{{id}}`）
3. 最多显示4篇
4. 若无同标签文章，回退查询最新文章作为补充
5. 自定义"相关文章推荐"标题和图标

**数据来源**：Ghost 内置内容查询助手，无需额外 API 调用，服务端渲染，性能好。

**为什么放在主题层而非修改核心**：
- 相关推荐是展示逻辑，属于视图层职责
- Ghost `{{#get}}` 助手已提供足够的查询能力
- 放在主题中可随时调整推荐算法，不影响核心稳定性
- 升级 Ghost 时不受影响

#### 3.3.2 搜索增强

**实现位置**：`assets/js/oss-search.js` (401行) + `assets/css/oss-custom.css`

**功能特性**：
1. **搜索弹窗**：点击搜索按钮或按 `Ctrl/Cmd+K` 打开模态框
2. **关键词高亮**：搜索结果中匹配的关键词用 `<mark>` 标签高亮显示
3. **无结果建议**：搜索无结果时显示热门标签建议，点击可自动搜索
4. **键盘导航**：上下箭头选择结果，Enter 跳转，ESC 关闭
5. **防抖搜索**：300ms 延迟，避免频繁 API 调用
6. **加载状态**：搜索中显示加载动画

**技术实现**：
- 使用 Ghost Content API（`/ghost/api/content/posts/`）查询
- 使用 `filter=title:~keyword,excerpt:~keyword` 进行模糊匹配
- Content API Key 通过 `data-content-api-key` 属性注入，**不使用 Admin API Key**
- 纯前端实现，无需额外服务端

**安全考虑**：
- 仅使用 Content API Key（只读权限），不暴露 Admin API Key
- 搜索结果文本进行 HTML 转义，防止 XSS
- API Key 设计上就是前端可用的，仅能读取公开内容

## 六、问题与反思

### 6.1 遇到的主要问题

| 问题 | 原因 | 解决方案 | 经验教训 |
|------|------|----------|----------|
| Node.js 版本不兼容 | 系统默认 Node 24，Ghost 6.x 要求 Node 22 | 下载 Node 22 便携版，创建包装脚本 | 开源项目版本兼容矩阵是硬约束，必须以官方声明为准 |
| 原生模块编译失败 | 系统未安装 VS C++ 构建工具 | 设置预编译二进制镜像，下载预编译版本 | 优先使用预编译二进制，避免本地编译依赖 |
| 管理后台加载慢 | Ember.js 应用首次加载需下载大量 JS | 等待30-60秒，或刷新页面 | 这是上游项目特性，不影响功能，演示时需预留时间 |
| ActivityPub 警告 | Ghost 6.x 新功能在本地环境获取 webhook secret 失败 | 忽略非致命警告，核心功能不受影响 | 区分致命错误和非致命警告，不被警告干扰 |
| gscan 安装失败 | 网络环境限制 | 跳过自动校验，基于上游主题保障兼容性 | 自动化工具受环境限制时，需有手动验证兜底 |

### 6.2 实验收获

1. **开源项目评估能力**：学会从许可证、社区活跃度、文档质量、技术栈匹配度、版本兼容矩阵等维度评估开源项目的适用性，不再仅凭 Star 数做判断。

2. **源码阅读与定位能力**：通过阅读 Ghost 主题结构、Handlebars 助手文档、Content API 文档，学会在大型开源项目中快速定位需要修改的模块，建立"修改边界"意识。

3. **二次开发方法论**：深刻理解了"扩展而非修改核心"的开源开发模式。通过主题层和 API 集成实现功能扩展，既保证了上游可升级性，又使个人贡献清晰可辨。

4. **版本管理规范**：实践了 Feature Branch、Pull Request、Code Review、Conventional Commits、版本标签等完整的 Git 工作流，养成了规范的提交习惯。

5. **可复现交付意识**：学会编写让第三方无需口头询问即可复现的 README，包括固定版本、环境要求、安装步骤、演示数据、测试方法、已知问题等完整信息。

### 6.3 不足与改进方向

1. **自动化测试不足**：当前测试为人工验收测试，未来可引入 Playwright 进行 E2E 自动化测试，提高测试可重复性。

2. **中文搜索效果有限**：基于 SQLite LIKE 的搜索对中文支持有限，只能精确匹配连续字符。未来可引入 Elasticsearch 或中文分词器改进。

3. **相关推荐算法简单**：当前仅基于 primary_tag 单标签匹配，未来可优化为多标签加权匹配、阅读时长权重等更智能的推荐算法。

4. **gscan 主题校验未完成**：受网络环境限制未能运行 gscan，未来在良好网络环境下应补全自动主题校验。

5. **生产环境部署未涉及**：实验仅在本地开发环境运行，未来可学习使用 MySQL、Nginx、Docker 等进行生产环境部署实践。

## 八、思考题回答

### 思考题1：为什么选择修改主题或伴随服务，而不是直接修改 Ghost 核心？这种边界对升级有什么影响？

**回答**：
1. **职责分离**：主题负责展示逻辑，核心负责业务逻辑。相关推荐、搜索增强属于展示层需求，放在主题中更合适。
2. **可升级性**：Ghost 核心频繁更新（平均每月一个版本），如果直接修改核心，每次升级都需要手动合并冲突，维护成本极高。主题通过稳定的 API 和助手与核心交互，升级核心时主题通常无需修改。
3. **可维护性**：个人修改集中在主题目录，代码量小、边界清晰，便于 Code Review 和问题定位。
4. **社区贡献**：如果修改有价值，可以单独将主题开源分享，不涉及核心代码的分叉。
5. **风险隔离**：主题代码出错最多导致前台显示异常，不影响核心数据和管理后台，风险可控。

**对升级的影响**：主题层修改使得 Ghost 核心可以无缝升级，只需关注主题使用的 API 是否有破坏性变更（通常 Ghost 对主题 API 保持向后兼容）。

### 思考题2：RealWorld 的统一 API 规范和 Ghost 的完整产品路线分别适合哪些教学目标？

**回答**：
- **RealWorld 规范路线**适合教学"全栈开发能力"和"API 设计思维"。学生需要从零选择技术栈实现完整的前后端，理解 RESTful API 设计、前后端分离、数据模型设计等。适合有较强编程基础、希望深入理解 Web 应用内部实现的学生。
- **Ghost 产品路线**适合教学"开源软件二次开发能力"和"工程化思维"。学生学习如何评估成熟开源项目、在既定架构下做扩展、遵守修改边界、利用现有 API 和主题机制。适合希望快速产出可用成品、学习开源协作模式的学生。

本实验选择 Ghost 路线，因为课程目标是"开源软件获取、使用、分析与规范开发"，Ghost 路线更贴合这一目标。

### 思考题3：如果搜索改为服务端全文索引，数据一致性、隐私和部署复杂度会发生什么变化？

**回答**：
1. **数据一致性**：服务端全文索引（如 Elasticsearch）需要维护索引与数据库的一致性。文章创建、编辑、删除时都需要同步更新索引，需要处理索引更新失败的补偿机制，增加了系统复杂度。当前前端搜索直接查询 Content API，数据始终是实时一致的。
2. **隐私**：服务端索引需要将文章内容（包括会员专属文章）索引到搜索引擎，需要严格控制索引范围和搜索权限，防止未授权内容通过搜索泄露。当前前端搜索仅查询公开文章，权限由 Ghost API 天然控制。
3. **部署复杂度**：需要额外部署和维护 Elasticsearch 服务，增加了内存、存储和运维成本。当前方案零额外服务，仅需 Ghost 本身即可运行。
4. **搜索质量**：服务端全文索引支持中文分词、相关性排序、模糊匹配等高级功能，搜索质量远优于 SQLite LIKE。当前方案在中文搜索效果上有明显局限。

**权衡**：对于个人博客和实验环境，当前前端搜索方案在复杂度和功能之间取得了合理平衡。如果是大型内容平台，值得引入服务端全文索引来提升搜索体验。

### 思考题4：如何用 Git 证据区分"安装配置"、"界面修改"和"具有工程价值的二次开发"？

**回答**：
1. **看提交内容和文件路径**：
   - 安装配置类提交通常只修改配置文件（.gitignore, .env.example, config文件），代码量小，无业务逻辑
   - 界面修改类提交主要修改主题模板（.hbs）和样式（.css），可通过 diff 看到具体的视觉改动
   - 具有工程价值的二次开发通常包含新的逻辑代码（.js）、算法实现、错误处理、测试用例，代码量较大且有明确的功能设计

2. **看提交信息规范**：
   - 规范的 Conventional Commits 可以直观区分：`chore:` 是配置，`feat(theme):` 是界面功能，`feat(enhancement):` 是工程功能
   - 每个提交有明确的范围和描述，便于追溯

3. **看分支和 PR 结构**：
   - 不同类型的工作在不同分支完成，通过 PR 合并，每个 PR 有明确的目标和审查记录
   - 本实验中 `feature/theme-customization` 分支是界面修改，`feature/blog-enhancement` 分支是工程二次开发

4. **看测试和文档配套**：
   - 具有工程价值的二次开发通常配套有测试用例、设计文档、Issue 验收条件
   - 本实验的自主扩展功能都有对应的测试用例（TC-019, TC-020）和设计说明

5. **看可复用性和抽象程度**：
   - 界面修改通常是特定于本项目的样式调整
   - 工程二次开发通常有一定的抽象和可复用性，如搜索增强组件可以迁移到其他 Ghost 主题
